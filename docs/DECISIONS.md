# Decisions log

Short ADR-style notes. These feed the README sections the brief requires.

| # | Decision | Why | Status |
|---|----------|-----|--------|
| 1 | JavaScript (ESM) + Zod, no TS build step | `npm run evaluate` must run from a clean clone with zero setup; Zod gives runtime validation of untrusted model output, which TS types cannot | decided |
| 2 | npm workspaces monorepo (`server`, `web`) | One install step, one repo, shared root `.env` | decided |
| 3 | Single `runPipeline()` shared by web + CLI | Brief forbids a parallel implementation | decided |
| 4 | Node built-in test runner | No test deps; fast | decided |
| 5 | Deterministic: `allocateSchedule`, `checkCoverage` | Brief: must not be handed to the model | decided |
| 6 | Edit-state: `origin` (generated/edited/user) + `pinned` on questions/flashcards | Regeneration replaces only `generated && !pinned` items in the target section | proposed (Phase 6) |
| 7 | LLM: one OpenAI-compatible client, presets for Gemini (default, `gemini-2.5-flash`) and Groq (`openai/gpt-oss-120b`) | Groq free tier is ~8k tokens/min per model, which makes "5 cases in 15 min" tight; Gemini's free token budget is far larger but ~10 requests/min. Both supported so a reviewer can use whichever key they have | decided |
| 8 | Practice ordering: confidence-weighted sort vs SM-2 | TBD in Phase 7 | open |
| 9 | Coverage loop: at most 3 repair rounds (a pass = one coverage check, so <= 4 checks + 1 after templating). Round 1 fills every gap in batches; rounds 2-3 target uncovered must-haves one requirement per call. Stops when nothing is uncovered, rounds are spent, or the provider reports a fatal error (quota/auth/bad request) | Three escalating attempts catch a model that skipped or mis-tagged a requirement without burning a free-tier budget on a requirement it will never address; the exit conditions are all checked in code | decided |
| 10 | Public discussion source | TBD in Phase 2 (must respect ToS/robots) | open |
| 11 | Auth = bcrypt + stateless signed JWT in an httpOnly cookie (7d expiry) | Minimal per brief; no session store to run. Trade-off: no server-side revocation (logout just clears the cookie) | decided |
| 12 | Cookie `SameSite=None; Secure` in prod + Origin check on non-GET | Web and API deploy to different origins; Origin check stands in for SameSite as CSRF defence | decided |
| 13 | Repo interface (`repos/mongo.js` / `repos/memory.js`) injected into `createApp` | Route tests run without Mongo; persistence stays a separate concern | decided |
| 14 | Ownership enforced in the query (`{_id, userId}`); other users' kits return 404 not 403 | No existence leak; impossible to forget a check after the fetch | decided |
| 15 | Duplicate posting = unique index on (userId, sha256(normalised jd + company url)); POST returns the existing kit with `duplicate: true` | Idempotent even under double-click races; `days` isn't part of the hash (re-scheduling is a regenerate, not a new kit) | decided |
| 16 | Single `httpClient.httpGet` is the only network path: guard on every redirect hop, per-host throttle, timeout, content-type allow-list, streaming size cap | Section 11 controls live in one auditable place; fetchPage/crawler/robots/discussion all reuse it | decided |
| 17 | SSRF guard resolves DNS and rejects if ANY record is non-public; blocks IPv4-mapped IPv6 and decimal-IP forms | Covers the common bypasses. Known gap: resolve-then-fetch is not pinned, so DNS rebinding is not fully closed | decided |
| 18 | Private-address blocking defaults to ON only when NODE_ENV=production | Brief requires rejection in production but `evaluate` must crawl localhost fixtures from a clean clone | decided |
| 19 | Crawl = best-first by link score (URL words + anchor text), pages that look like hiring pages boost their own links, sitemaps seed extra candidates | "Fixed list of paths is not sufficient"; finds `/careers -> /handbook/.../interviewing` and sitemap-only pages | decided |
| 20 | Hiring page chosen by page-TEXT evidence (`hiringSignals` >= 6), not by URL | A page named /careers that is only job listings must not count as "how they hire" | decided |
| 21 | robots.txt: 4xx = allow, 5xx = disallow, network error = surface as unreachable; cache lives for one run | RFC 9309; avoids stale rules across kits | decided |
| 22 | Crawl scope: same registrable domain (subdomains ok); localhost/IP hosts are confined to the start path prefix | Handbooks live on subdomains; local fixtures serve several companies from one host | decided |
| 23 | Public discussion = Hacker News Algolia API only (no Reddit/Glassdoor) | Official public API, no scraping; those sites restrict automated access. Precision filter: must name the company AND mention interviewing | decided |
| 24 | Unreachable company site is NOT a failed case; `researchCompany` returns `gaps[]` and the kit says so | Brief: "unreachable sites are recorded rather than fatal"; failed is reserved for no kit at all | decided (confirm in Phase 5) |
| 25 | LLM client owns: sliding-window token + request budget, retry/backoff honouring provider hints, quota-exhausted fast-fail, JSON extraction, schema validation, ONE repair call, truncation retry with more `max_tokens`, drop-unsupported-param fallback | Section 10 "invalid JSON", "rate-limits or briefly fails"; every step goes through one entry point (`completeJson`) | decided |
| 26 | The model proposes, code decides: ids assigned by code; a requirement is kept only if its quoted evidence is found in the posting; explicit wording ("Bonus:", "Nice to have" heading, "required") overrides the model's priority | Extraction is 20 of 55 automated points and "nothing invented" is part of it | decided |
| 27 | Category plan is deterministic (`planCategories`); each category has its OWN system prompt; hiring-process signals (regex over fetched text) and seniority change which categories exist | Brief: technical vs behavioural must not share a call; a published take-home + system design round must produce a different kit | decided |
| 28 | Model may only cite requirement ids it was given; unknown ids removed, a question left with none is dropped (never re-attached) | Keeps coverage checkable rather than a matter of opinion | decided |
| 29 | Untrusted text (JD, pages, forum snippets, even requirement text) is only ever sent inside `<<<UNTRUSTED label id>>>` blocks with a random id; lookalike delimiters defused; system prompt says never to follow instructions inside | Section 11 | decided |
| 30 | Company brief makes NO model call when there are no usable pages; cited sources must be a subset of pages supplied | "Honest brief rather than a fabricated one" | decided |
| 31 | Only requirement extraction is fatal in the draft; brief/category/flashcard failures are recorded in `failures` and the draft continues | Lets Phase 4's coverage loop retry gaps; `failed` is reserved for no kit at all | decided |
| 32 | Kit extension: optional `research` block (gaps, hiring page, discussion sources, skipped sources, thin_description) | Lets a thin or poorly-researched kit say so inside the kit itself | decided |
| 33 | Escalation instead of "stop when a round makes no progress" | A no-progress round says little about a stochastic model; changing the request (batch -> single requirement) is a better second try than quitting | decided (refines #9) |
| 34 | Nice-to-have gaps are attempted in round 1 only; if still uncovered they are listed in `coverage.uncovered_requirement_ids` and `research.gaps`, never forced | Must-haves are the contract; padding nice-to-haves with filler would be dishonest | decided |
| 35 | Last resort for a still-uncovered MUST: a fixed template question, flagged `template: true`, and named in `research.gaps` | The brief says a kit shipping uncovered must-haves has failed; a visibly generic question is better than an uncovered must-have, and it is deterministic code, not invented content | decided |
| 36 | Schedule: priority order (covers a must, then difficulty, then original order) cut into consecutive blocks of ~equal study time; fewer questions than days -> one question per study day, then REVIEW days cycling the same order | Exactly N days always; harder/higher-priority first so the last day is the lightest; a 60-day plan for 12 questions is mostly review rather than empty days | decided |
| 37 | Minutes are integers derived from difficulty (10/15/25 per question; review days half, rounded up) | No model estimate; reproducible | decided |
| 38 | Batch: ONE LLM client (shared token budget) for all cases, cases run sequentially, evaluate logic split into `evaluateCore.js` (tested) and a thin CLI | Per-case clients would each start with a fresh budget and trip the provider limit at case boundaries | decided |
| 39 | Generation runs as an in-process background job (queue + concurrency cap); POST only creates a `pending` record and returns | Generation takes tens of seconds to minutes and fails halfway; the request must not hold open. Trade-off: a single API instance (free tier). A multi-instance deploy would need a real queue | decided |
| 40 | Client POLLS `GET /kits/:id` (1.5 s) instead of SSE/WebSocket | Works through any free-tier proxy, survives reloads and server restarts, and the progress is just persisted state. Cost: up to 1.5 s latency | decided |
| 41 | Job state machine is made of single conditional updates: `claim` (pending->running), and `setProgress`/`finish`/`fail` that only apply to the CURRENT attempt of a RUNNING kit | A double trigger can't run twice; a timed-out or superseded run can't overwrite a newer one; deleting mid-run is a no-op | decided |
| 42 | Same posting twice: unique index on (user, input hash) + `claim` atomicity + in-memory enqueue guard (three layers) | "Triggered twice for the same posting"; each layer covers a different race | decided |
| 43 | Progress stored as `{step: {status, detail, seq}}` (latest per step) | Bounded size across retries; UI sorts by `seq` | decided |
| 44 | Restart recovery: `running` -> `pending` and re-enqueue, up to `JOB_MAX_ATTEMPTS`, then `failed: JOB_INTERRUPTED` | A crash mid-generation neither hangs the kit forever nor loops forever | decided |
| 45 | Soft time budget: optional steps skip themselves late (flashcards at 55%, new categories at 80%, nice-to-have gap rounds at 70%, any repair at 95%); must-have coverage then comes from instant template questions; every skip is written into `research.gaps` | Degrade a kit honestly instead of missing the deadline (jobs: 80% of `JOB_TIMEOUT_MS`; batch: remaining time shared equally by remaining cases, floor 30 s) | decided |
| 46 | Per-user cap on active jobs (default 5) and max 10 rows per upload | Free-tier budget protection; abuse control | decided |
| 47 | Repo contract test runs against memory always and against Mongo when `TEST_MONGODB_URI` is set | The Mongo repo can't be exercised in every environment; the same behavioural contract keeps both honest | decided |
| 48 | Edit state per item: `origin` (`generated` / `edited` / `user`) + `pinned`. A regeneration replaces exactly `origin != edited/user AND not pinned` (`isReplaceable`). Editing, moving between categories, or writing an item marks it; pinning protects without marking | The brief's "hardest state problem". One rule, one function, used by server and browser | decided |
| 49 | The edit rules live in a shared workspace package (`@prepkit/shared/kitOps`), imported by the server (authoritative) and the browser (optimistic) | The UI can apply an edit instantly with exactly the rules the server will apply; the server tests cover what the browser runs | decided |
| 50 | Edits are ID-addressed ops (`update_question`, `move_question`, ...), never "replace the whole kit"; a batch is atomic | Edits to different items commute, so two tabs (or an edit during a regeneration) merge instead of clobbering | decided |
| 51 | Every post-generation write goes through `applyToKit`: read -> copy -> mutate -> validate against Appendix A -> write only if the version is unchanged, else re-read and re-apply (<= 8 tries) | Optimistic concurrency (CAS on a `version` counter) without locks; a conflicting writer re-applies on the NEW document | decided |
| 52 | Regeneration decides what to delete at COMMIT time against the latest document, not the snapshot the model saw | Anything the user edited/wrote/pinned while the model was thinking survives; deletions made meanwhile aren't resurrected | decided |
| 53 | A regeneration that yields nothing, fails, or loses its source (site down) changes nothing (REGEN_EMPTY / REGEN_NO_NEW_INFO) | Regenerate must never leave the user with less than they had | decided |
| 54 | After a category regeneration the coverage check runs for THAT category's requirements only | Doesn't refill what the user deliberately deleted elsewhere | decided |
| 55 | Edited brief: regenerate asks for confirmation (`force`); if the user edits it WHILE it regenerates, their version wins (REGEN_SUPERSEDED_BY_EDIT) | "Regenerating one section must not discard edits" applies to the section being regenerated too | decided |
| 56 | Schedule is derived from questions: after question changes it re-flows deterministically, but days the user edited keep their focus/minutes; "Rebuild schedule" is the explicit from-scratch action (and can change the day count) | Deleting/adding a question must show up in the plan without destroying hand edits | decided |
| 57 | New items get CLIENT-chosen ids (`q-xxxx`, `f-xxxx`); the server accepts them if unused | Follow-up edits to a just-added item never need a temp-id swap; regenerated ids are random too, so ids are never reused | decided |
| 58 | Client: optimistic apply -> ops sent strictly in order -> server version replaces local when the queue drains; polls are ignored while edits are in flight; a rejected edit drops the queue, shows the error and reloads | Instant-feeling edits without letting a background poll overwrite what the user just typed | decided |
| 59 | Reordering = arrow buttons (not drag and drop); categories change via a select | Keyboard- and screen-reader-operable by default; drag and drop would be an enhancement | decided |
| 60 | Requirements are read-only in the builder; flashcards have no per-section regenerate | Editing requirements would invalidate coverage semantics; scope | decided (limitation) |
